# Mobile CI lessons

Every iPad or iPhone CI or build failure goes here, with its cause and fix, so it doesn't happen twice. Mac jobs are scarce (README, "Building"): read this before pushing mobile work. Newest first.

## Compiling

- **Nov 21: "invalid redeclaration of 'tries'"** (phone-check build on abcdfc1). A scroll loop added to `TasksLookTests.run` declared `var tries` in a function that declares it again further down. Fix: a different name (`swipes`). Before pushing a test edit, grep the whole function for the names you add.
- **Nov 21: "'+=' is not a prefix unary operator"** (build on 6efed44). `entry +=["", …]`: Swift reads an operator with a space on one side only as prefix or postfix, so `+=[` failed. Fix: a space on both sides of every binary operator (`entry += [`). Before pushing, grep the added lines for an operator with a space on one side only (`git diff -U0 | grep '^+' | grep -P '\S(\+=|==|&&)\s|\s(\+=|==|&&)\S'`).
- **Nov 21: "'async' call in an autoclosure that does not support concurrency"** (build on 312d996). `guard a || (await f())`: the right side of `||` is an autoclosure, which can't `await`. Fix: await into a variable first (`var ok = true; if !a { ok = await f() }`). Linux can't build the app, so read every new `await` for this before pushing.
- **Nov 21: "invalid redeclaration of 'RecordingBar'"** (build on 50ebdd2). The new Recordings code named its top bar `RecordingBar`, a name the tutor's board recorder (`Sources/Tutor/BoardRecorder.swift`) already used; the app target is one module, so the clash also broke that file's lines ("requires that 'RecordingBar' conform to 'View'"). Fix: renamed to `RecordingTopBar`. Before pushing a new type, grep `Sources` and `Packages/NexusCore/Sources` for `(struct|class|enum) <Name>\b`: Linux can only build the core, so a clash in the app shows first on the Mac.

## Time limits

- **Nov 21: phone-check's iPhone "Run the tests" hit its 25-minute limit** (PR #46, cc88bbf). The new look (PR #45) and Recordings together added 15 iPhone test classes; the run was cut off mid-`TasksLookPhoneTests`, so no xcresult and no screenshots. Fix: step 45, job 60. When a PR adds a test class, check the matching step's limit in both ui-check.yml and phone-check.yml.
- **Nov 21: `RecordingsTests.testRecordings` failed "Failed to get screenshot: Timed out while requesting screenshot"** (ui-check on f6947c7, iPad only; the iPhone passed the same test). The simulator didn't answer XCTest's screenshot call; nothing in the app or the test changed there. Fix: none in code; the next push re-ran it. If `shot()` times out twice in a row, read the freeze reports first (a stuck main thread also stops screenshots).

- **Nov 19: "The job was not acquired by Runner of type hosted even after multiple attempts"** (ui-check on 0f84b86). GitHub had no Mac free for 15 minutes and failed the run before a single step; nothing in the repo caused it. Fix: re-run the run (Actions › the run › Re-run), don't push to retrigger. Whoever pushed should check the run is actually running, not just queued: this one sat failed overnight because the failure looked like any other.
- **Nov 19: ui-check's iPad step hit its 70-minute limit, the iPhone step its 40.** Every test that ran passed; the runner was slow (the same tests took up to twice as long as on Nov 18), so `TutorPanelTests.testTutorChatDark` and `TimeTrackingPhoneTests` were cut off. Fix: iPad step 95, iPhone step 55, job 170. When the suite grows, raise these with it: a limit is for a hung run, not for a slow Mac.
- **Nov 18: the iPhone step hit 25 minutes** on main (12 tests, about 26 minutes). Raised to 40, job 130 (PR #42).
- **Nov 20: `BoardSaveSpeedTests.testAFullBoardSavesQuickly` failed with "Failed to get matching snapshots: Timed out while evaluating UI query"** (PR #44 after main was merged in, a6f3ba7). It is the first look after the test's 150 s wait, while the app is still saving the big board; the test passed on the same branch's two runs before, and the Nov 16 note in the test is the same failure. Fix: re-run the failed job (the re-run passed). If it fails like this twice in a row on a quiet day, the saves got slower: read the bench numbers before touching the wait.
- **Nov 20: ui-check's iPad step hit its 95-minute limit** (PR #44, 06ee70c). Every test that ran passed, but `RichTextTests` took 1064 s and 1152 s, against 139 s and 144 s on the same code an hour earlier (the step from "reopened on the board" to "whole block closed" alone took 310 s in both themes), so the tutor tests were cut off. The iPhone step passed. Fix: re-run the failed job (Actions › the run › Re-run failed jobs), no push; the re-run passed in 78 minutes. If `RichTextTests` is that slow twice in a row, look at that test's waits, not the limit.
- **Nov 20: `SidebarTreeTests.testNestedNotebooksLight` failed on "Week 1's boards still show when it is closed"** (PR #44, which doesn't touch the sidebar tree). The same test in dark passed two minutes earlier in 117 s; the light run took 325 s, opening "School" took 29 s instead of 3, and the 5-second wait for the closed level ran out on a stalled simulator. Fix: that wait is 20 s. A test that passes in one theme and times out in the other in the same run is the runner: lengthen the wait for content, never drop the check.
- **Nov 21: `SidebarTreeTests.testNestedNotebooksLight` failed on "Week 1 didn't open"** (PR #45, 14244a0), the same shape as Nov 20: dark passed in 107 s in the same run, light stalled on the 5-second wait for the arrow to turn. Fix: that wait is 15 s too.
- **Nov 18: `ApplicationsPhoneTests` failed with a simulator launch timeout**, not an assertion. A re-run passed it. Read the failure line before changing code: "Failed to launch" or "timed out waiting for the app to idle" is the runner, not the app.

## Writing UI tests

- **Nov 21: `SidebarSpeedTests.testManyBoards` failed "open a notebook never showed"** (ui-check on 172c329, iPad). Recordings' new sidebar row pushed the first notebook down, so `reach` stopped as soon as its row was hittable, right at the foot of the sidebar, and the tap on its arrow didn't open it (the new look's footer icons sit there). Fix: `reach` lifts a row that is within 140 points of the bottom with one more swipe. A test that scrolls to a row should leave it clear of the edges before tapping.
- **Nov 21: then "open a notebook took too long" (13.08 s, limit 8; 3.4 s on the new-look branch)** (ui-check on 8ea9ed6). The freeze reports: at launch the main thread was in `RecordingsCount.review`, formatting `snapshot.loadedAt` into its cache key (`"\(date)"` builds a locale date formatter, ICU's first load), then 20 s loading SF Symbol glyphs, and 4.3 s laying out the opened notebook's rows (ICU's first line breaker), all slow first loads on that runner. Fix for our part: the count's key is plain numbers (`timeIntervalSince1970`), as AppsData's already was. Never put a Date into a string in a view's body; read the freeze reports (step "Freeze reports the app wrote") before calling a timing failure slowness.
- **Nov 21: the sample folder is shared by every test on one simulator.** `makeSample()` runs only when there's no data folder yet, so what one test writes stays for the next. Recordings' Accept filed two tasks, and `TasksLookPhoneTests` then couldn't see "Columbia short answers" (pushed below the fold); after Accept, Recordings' own "Tasks added" sat below the list's scroll position. Fix: scroll to (reveal) an element before asserting it, and never assume the sample is untouched.
- **SwiftUI lists and forms only create the rows on screen.** A row below (or above) the fold doesn't exist for XCTest: scroll until it appears, both ways, with a bounded loop (`while !row.waitForExistence(timeout: 3) && n < 6 { app.swipeUp() }`). Nov 18-19: Study's R1 row, Upload's "File it", the workstream page's Spanish link after setting Spanish up.
- **Nov 20: `ScanTests` failed "the board made from the scan didn't open"** (ui-check on d6ed389). The app had made the board; then the simulator's main thread sat 54 s in accessibility loading (the freeze report's stack: `UISheetPresentationControllerAccessibility`, `AXMobileQuickLookGlue`), right across the test's 30 s wait. The freeze reports printed after the iPad step show this: read them before blaming the app. Fix: a wait right after something heavy (a PDF, a scan, a picture) gets 120 s, and a test takes a screenshot of what was there before it fails, so the next failure shows its state. The run after that opened the board, and the second scan's camera too, then missed the board's "Reading the handout…" toast, which is up for under 2 s. Check what stays (here the page pill naming the new printout), not a toast.
- **Nov 21: `RecordingsTests` failed "the seeded class isn't listed"** (ui-check on 5eef118, iPad and iPhone). The test looked for rows by the title Claude prepared ("Redox: writing half-equations"), but the list showed recording.json's own title, which stays "Class" or "Meeting" until Accept. The screenshot (rec-1-list) showed it at once. Fix: a recording waiting for review is listed by its prepared title, as on the laptop. Before pushing a test that finds a row by its text, check which field the row actually shows, and read the step's screenshot before anything else when it fails.
- **Nov 21: `RecordingsTests` failed "no Accept on the meeting" and "recording didn't start"** (ui-check on 330db79). Accept sits at the foot of the review form, so the list hadn't made it yet when the test waited for it (filing worked once `reveal` scrolled to it). Recording asked for the microphone even in the demo, a system alert nothing tapped. Fixes: scroll before asserting a row low in a form; a demo mode asks for no permission it doesn't use.
- **Wait for content, not a fixed sleep.** A web tool page (VSEPR) screenshotted after `sleep(5)` came out blank; wait for `app.webViews.firstMatch.staticTexts.firstMatch`.
- **An `accessibilityIdentifier` on a VStack hides its children's ids**: add `.accessibilityElement(children: .contain)`.
- **Nov 20 (new look, PR #45): an `accessibilityIdentifier` on an HStack row goes to every child, buttons included.** The subject row's id landed on its arrow, so `el("subject-…").tap()` opened the folder instead of stepping inside, and the name's static text lost its label match (`staticTexts["Physics HL"]` failed in SpanishPadTests). Fix: no id on a row that holds a button and a name; tests tap the name's text.
- **Nov 20: a view that fills a whole fan (or any big container) is found at its frame's centre.** The quick ring's choices were full-fan views with an overridden `accessibilityFrame`; XCTest tapped the fan's middle (the ring's own button) and nothing was picked. Fix: the small chip is the accessibility element.
- **Nov 20: a wider font (Onest) pushed buttons below a scroll view's fold.** The Spanish memory review's Save sat at the bottom of a 420 pt scroll area; on the iPhone it ended under the tab bar and the tap missed. Fix: the review's buttons sit under the scrolling part. After a font or spacing change, expect tests that tap near the bottom of a sheet to need a look.
- **Nov 20: a row that fills up with more controls stops being hittable at its end.** The bar's Draw row took the tools, ten colours and six sizes plus the pills; Extra bold went off screen and PenOptionsTests' width checks failed. Fix: Insert space and + moved to Insert, page and zoom to the top row.
- **Nov 20: a query over every button with a label can time out ("Timed out while evaluating UI query").** NewLookTests' `button("Pen")` (all matches, then `isHittable` on each) timed out right after the quick ring's double tap, while the board was busy redrawing. Fix: the bar's tool buttons have ids (`board-tool-<tool>`), and the test asks `app.buttons["board-tool-pen"].firstMatch` with a wait. Prefer an id query to a label scan wherever a screen has many buttons.
- **Nov 21: when a screen shows one title in several parts, ask inside the part.** The new Today shows a task in Next up, the list, the day's hours and Tomorrow, so `app.staticTexts["Try the iPad planner"].firstMatch` could be Next up's, above the list, and DayOrderTests' order check would fail depending on the clock. Fix: `app.otherElements["today-list"].staticTexts[...]` (the part has `.accessibilityElement(children: .contain)` and an id).
- **Nov 21: three new-look test failures on 284308b (PR #45), all in the tests.** (1) TasksLookTests asked for `lens-all`; the lens ids use the lens's raw value (`lens-All`, `lens-No date`). Read the id's source before writing the query. (2) TodayLookPhoneTests' Slipped check found "Nothing slipped": earlier iPhone tests on the same simulator share the sample folder and had already planned the slipped task again. A test that needs sample state another test may change says so and skips, with a screenshot, instead of failing. (3) SidebarSpeedTests' "Page 04's row isn't the selected one" while the screenshot showed it selected: the sidebar's Recent section lists Page 04 too, above the notebook's row, and `cells.containing(...).firstMatch` took that one. Fix: ask for a selected cell that holds the name.
- **Tests share the simulator's UserDefaults.** A test that opens something remembered (a subject's folder) changes the next test's sidebar; the test hooks reset it (`-NexusTestNestedNotebooks` clears `openNotebooks` and `openSubjects`).
- **When a screen's way in changes, change every test that goes there.** Nov 19: the sidebar lost its Study tools and Spanish rows, so the Spanish tests open Spanish from the class's Study page (`study-spanish`).
