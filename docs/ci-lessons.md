# Mobile CI lessons

Every iPad or iPhone CI or build failure goes here, with its cause and fix, so it doesn't happen twice. Mac jobs are scarce (README, "Building"): read this before pushing mobile work. Newest first.

## Compiling

- **Nov 23: "overlapping accesses to 'c', but modification requires exclusive access"** (build on 874fda4, PR #59). `c?.percentEncodedQuery = c?.percentEncodedQuery?.replacingOccurrences(…)` on an optional `URLComponents` reads and writes `c` in one statement; through optional chaining that is an exclusivity error. Fix: read into a local first (`let encoded = c?.…; c?.percentEncodedQuery = encoded`). Before pushing, grep the added lines for `x?.a = x?.…` on a `var` struct.
- **Nov 21: "invalid redeclaration of 'tries'"** (phone-check build on abcdfc1). A scroll loop added to `TasksLookTests.run` declared `var tries` in a function that declares it again further down. Fix: a different name (`swipes`). Before pushing a test edit, grep the whole function for the names you add.
- **Nov 21: "'+=' is not a prefix unary operator"** (build on 6efed44). `entry +=["", …]`: Swift reads an operator with a space on one side only as prefix or postfix, so `+=[` failed. Fix: a space on both sides of every binary operator (`entry += [`). Before pushing, grep the added lines for an operator with a space on one side only (`git diff -U0 | grep '^+' | grep -P '\S(\+=|==|&&)\s|\s(\+=|==|&&)\S'`).
- **Nov 21: "'async' call in an autoclosure that does not support concurrency"** (build on 312d996). `guard a || (await f())`: the right side of `||` is an autoclosure, which can't `await`. Fix: await into a variable first (`var ok = true; if !a { ok = await f() }`). Linux can't build the app, so read every new `await` for this before pushing.
- **Nov 21: "invalid redeclaration of 'RecordingBar'"** (build on 50ebdd2). The new Recordings code named its top bar `RecordingBar`, a name the tutor's board recorder (`Sources/Tutor/BoardRecorder.swift`) already used; the app target is one module, so the clash also broke that file's lines ("requires that 'RecordingBar' conform to 'View'"). Fix: renamed to `RecordingTopBar`. Before pushing a new type, grep `Sources` and `Packages/NexusCore/Sources` for `(struct|class|enum) <Name>\b`: Linux can only build the core, so a clash in the app shows first on the Mac.

## Writing UI tests

- **Nov 23: a `-board.tool pen` launch argument pinned the tool** (`ExtrasPhoneTests`, PR #59): tapping the eraser did nothing, twice. A launch argument goes into UserDefaults' argument domain, which outranks what the app writes, so `BoardTools.tool` kept reading "pen". Fix: pass a setting as an argument only when the test never changes it; otherwise tap to it.
- **Nov 23: a swipe on the screen's middle didn't scroll an iPad form sheet** (`ExtrasTests` Google Docs panel): the middle of a medium-height sheet is its head, so the list stayed at 0% and the rows below never appeared (the hierarchy showed the scroll bar's value). Fix: swipe the sheet's own list (`app.collectionViews.containing(.any, identifier: …)`), and the iPad opens that panel at full height.
- **Nov 24: "Failed to swipe down CollectionView"** (`ExtrasTests`, the way back up to Sync now) and **a switch "not there" just under a row the test had scrolled to** (`widget-on` in Settings): a SwiftUI list only holds the rows near the screen, so a row scrolled away (or not reached yet) doesn't exist, and a list found by `containing(identifier: "gdocs-head")` stops matching once the head scrolls out, so the swipe has nothing to swipe. Fix: find the list by any of its rows (`containing(NSPredicate(format: "identifier BEGINSWITH 'gdocs-'"))`), and swipe (bounded) until the next row is hittable before asserting it; a plain tap doesn't reach a row that doesn't exist.
- **Nov 24: a UIMenu from the iPhone's tool pill brought the keyboard up over itself** (iOS 26 simulator, `ExtrasPhoneTests` +): the menu opened, then a keyboard slid up and covered it, with no element holding the keyboard's focus. The old check passed anyway (`exists` on "Insert space" without `isHittable`); the screenshot and the screen recording in the phoneshots showed it. Fix: + opens a sheet like the tools' (PhoneToolPill `openSheet(insert: true)`), and the test asserts the row is hittable and `app.keyboards.count == 0`. Lesson: assert `isHittable`, not `exists`, for something that should be on screen, and look at the picture even when a test passes.
- **Nov 23: `LiveActivityPhoneTests` failed "No matches found … Stop the timer"** (PR #59): the second press's tap re-resolved the button after the card had already changed. Fix: read its frame, then tap that place on the springboard.
- **Nov 23: `LiveActivityTests` (iPad) failed "Stop on the iPad's Lock Screen didn't stop the timer"** (ui-check on aa182b9, PR #54). The card showed on the iPad's Lock Screen and Allow was answered, but four coordinate taps on its Stop left the timer running. The test ran in landscape, where the springboard's screenshots come out rotated (the Lock Screen is drawn in the panel's portrait space), so a tap placed from the element's frame can't be trusted to land on the button. Fix: the test runs in portrait (every other iPad test sets its own orientation in setUp, so it doesn't leak), prints Stop's frame and takes a screenshot after the first press. Springboard tests on the iPad: portrait. Then (4f15af9) the Stop did stop the timer (the card turned to Up next), yet the test failed: it had left the app on See how it looks, whose example cards carry "Stop the timer" buttons, so the pill check found those. Fix: the test goes back to Settings first. Read the last screenshot before blaming the tap: it showed the card had changed.
- **Nov 23: `ChecklistLookPhoneTests.testChecklistLight` ("the oral card doesn't say when the last one was") and `DayOrderPhoneTests` ("the order dragged on the laptop wins over file order") failed** (phone-check on 8254eab, PR #52). Both passed in the same workflow an hour earlier (a5cc441) with no change to what they test. Fix: none in the PR; a run that crosses 04:00 UTC is re-run once. Making the sample hooks write for the day the test reads in would end it.

- **Nov 23: `TodayEdgesTests` (dark and light) failed "Tomorrow's strip shows 2 labels for five crowded tasks"** (full ui-check on b8a24d6, PR #52; the same two failed in PR #49's full run on Nov 22). Run alone on main (dispatch `only: TodayEdgesTests`, Nov 23 01:40 UTC) both passed, so it fails only after the other iPad tests have run on the same simulator, not because of either PR. To check one iPad test, wait for the iPad step's "Upload" to finish, then cancel the run; the iPad results are in its artifact's `shots/manifest.json` (`isAssociatedWithFailure`).

## Workflows

- **Nov 22: phone-check's iPad job failed on PR #49 with `StudyPadTests: no molecules row`**, as on every phone-check run since Nov 20 (runs 26-29, other PRs too): its Study test still looks for the Molecules row PR #42 took out of the sidebar. phone-check starts whenever a `UITests/*PhoneTests.swift` or `*PadTests.swift` file changes, beside ui-check, which already runs both devices.
